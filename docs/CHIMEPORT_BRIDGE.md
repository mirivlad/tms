# ChimePort: сервисная доставка уведомлений TMS (первый этап)

TMS остаётся источником идентичности пользователя. ChimePort сохраняет сообщения по паре (доверенное приложение, постоянный ID получателя), **не создавая пользовательских аккаунтов**. Пароли, логины и их хеши в ChimePort не передаются.

## Настройка администратора

1. Обновите ChimePort до версии с поддержкой `/api/v1/admin/external-apps` и выполните проверенный резервный снимок до миграции SQLite schema 4 → 5.
2. Войдите администратором ChimePort (API сессионным токеном) и создайте доверенное приложение: `POST /api/v1/admin/external-apps` с JSON `{"slug":"tms","origin":"https://tasks.example.org"}`. Сохраните возвращённый `cp_a_...` **один раз**. Он даёт право публиковать события всем получателям в пределах приложения и выпускать одноразовые пропуска — берегите его как административный секрет.
3. В окружении контейнера `notifier` TMS задайте `CHIMEPORT_BRIDGE_URL=https://chime.example.org` и `CHIMEPORT_BRIDGE_TOKEN=cp_a_...`; `APP_URL` TMS должен точно совпадать с `origin` доверенного приложения.
4. Убедитесь, что миграции TMS применены. После старта `bin/notify.php` новый отправитель инициализирует курсор текущим концом `internal_notifications`, чтобы не рассылать историю задним числом. Новые уведомления будут автоматически пересылаться через HTTPS.

Отправитель обрабатывает **единый канонический inbox TMS**, включая события задач и обсуждений. Неудачная отправка останавливает продвижение курсора; при повторе использует `Idempotency-Key`. Telegram и SMTP работают независимо. Деактивированные и неодобренные пользователи пропускаются.

## Что уже входит в протокол ChimePort

- У приложения есть собственный `cp_a_...` токен для `POST /api/v1/external/messages` с `recipient`, `title`, `body`, `priority`, `url`.
- Только зарегистрированный `origin` может встречаться в ссылках сообщений приложения; публикация ограничена по частоте.
- `POST /api/v1/external/tickets` (с токеном приложения): `recipient` + `code_challenge` (PKCE S256) → одноразовый ticket на 90 секунд.
- `POST /api/v1/external/exchange`: ticket + `code_verifier` → ограниченная сессия получателя на семь суток. `GET /api/v1/external/messages`, прочтение/непрочтение, Web Push, logout используют эту сессию.
- `PATCH /api/v1/admin/external-apps/{id}` с `{"disabled":true}` немедленно запрещает публикацию, обмен ticket и чтение существующими сессиями.

## Web Push на домене TMS

После подключения \`CHIMEPORT_BRIDGE_URL\` и \`CHIMEPORT_BRIDGE_TOKEN\` в окружении обоих сервисов TMS в **Настройки → Уведомления** появляется кнопка включения Web Push. Пользователь входит только в TMS, разрешает уведомления браузера и ничего не знает про аккаунты ChimePort. TMS регистрирует собственный \`/chimeport-sw.js\` и передаёт Web Push подписку доверенному ChimePort. Всплывающее уведомление содержит ссылку на TMS, а не ChimePort.

Для браузеров, поддерживающих Web Push, нужен общедоступный HTTPS TMS; на iOS требуется установка веб-приложения на домашний экран. Нельзя гарантировать мгновенную доставку при отключениях/энергосбережении.

## Android

В универсальном Android-приложении ChimePort теперь можно ввести обычный **адрес TMS**. Клиент обнаруживает \`GET /.well-known/chimeport.json\`, проверяет указанный сервис доставки, проверяет его неизменный \`instance_id\` и отправляет пароль только на \`POST /api/notifications/mobile/login\` самого TMS.

TMS проверяет свои учётные данные и ограничивает число неудачных попыток. Он передаёт в ChimePort лишь ID TMS пользователя вместе с S256 PKCE challenge; одноразовый ticket возвращается клиенту и обменивается им напрямую у ChimePort на семидневную scoped-сессию. Аккаунтов ChimePort для пользователей TMS нет.

Android хранит историю разных TMS-инстансов независимо, даже когда они обслуживаются одним ChimePort. Получатель читает/помечает свои сообщения через \`/api/v1/external/messages\` и слушает \`/api/v1/external/events\`. При истечении сессии пользователь заново входит в TMS.

**Ограничение MVP:** немедленный отзыв отдельных мобильных сессий при смене пароля TMS пока не реализован. Время жизни сессии ChimePort — до 7 суток. Администратор может отключить всё доверенное приложение целиком; в дальнейшем нужны отдельные управление устройствами и список отозванных сессий. Также требуется ещё проверить Android-сборку в CI и провести проверку доставки на реальном телефоне.

## Резервирование, обратная совместимость и retention

ChimePort обновляет SQLite schema 4 → 5, резервная копия должна сохранять связанный \`token-key\`. Старые обычные ChimePort-каналы, Android-сессии и интеграции MirvMon / Home Assistant не меняются.

Для новых внешних сообщений добавлена отдельная очистка через \`CHIMEPORT_RETENTION_DAYS\`; по умолчанию 30 суток. При отключении retention записи будут храниться без ограничения до ручного удаления.

**Ограничение MVP:** для ключа \`cp_a_\` пока нет ротации без перевыдачи приложения. Не меняйте его в БД вручную. Администраторам нужно держать этот ключ вне исходников, логов и браузера: он разрешает отправку событий любому пользователю данного приложения и выдачу пропусков.
