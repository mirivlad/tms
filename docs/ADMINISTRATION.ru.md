# Администрирование

## Первый администратор

Создайте первого администратора из контейнера приложения:

```bash
php bin/create-admin.php admin admin@example.com
```

После входа административные разделы доступны из пользовательского/административного меню.

## Пользователи и регистрация

Открытая регистрация управляется `REGISTRATION_ENABLED`.

При включённой регистрации ссылки подтверждения email строятся от `APP_URL`. Если `REGISTRATION_AUTO_APPROVE_AFTER_EMAIL=true`, подтверждение email одновременно одобряет аккаунт. Значение `false` требует ручного одобрения в **Администрирование → Ожидающие пользователи**.

Администратор может напрямую создавать пользователей, менять роль и активность, одобрять аккаунты, вручную подтверждать email, повторно отправлять письмо подтверждения, смотреть детали пользователя и временно входить от его имени для диагностики.

Пользователя нельзя отключить или удалить, если он остаётся единственным тимлидом хотя бы одной команды. Сначала назначьте другого участника тимлидом — это не позволяет административной операцией оставить команду без управления.

## Справочники и пользовательские поля

Статусы, типы задач, заказчики и дополнительные поля принадлежат конкретному пользователю. Они не становятся глобальными только потому, что владелец — администратор.

Для статусов доступны порядок, статус по умолчанию и статус завершения. Принадлежность статусов/типов/заказчиков защищается и приложением, и ограничениями БД.

Пользовательские поля: текст, многострочный текст, список, деньги, checkbox и список checkbox. При изменении набора вариантов значения, которые больше недопустимы, могут быть очищены/урезаны.

## SMTP

Откройте **Администрирование → Системные уведомления**. Укажите сервер, порт, TLS/SSL, логин/пароль и отправителя, включите транспорт, сохраните и нажмите **Отправить тестовое письмо SMTP**.

Пароль SMTP хранится зашифрованным. Ключ — либо внешний `NOTIFICATION_SECRET`, либо автоматически созданный ключ в volume `tms-secrets`.

## Telegram

Создайте бота через BotFather, затем задайте имя и token в **Администрирование → Системные уведомления**. Сначала используйте **Проверить соединение с Telegram**.

Для получения команд выберите один режим:

- **Long polling (рекомендуется):** TMS сам вызывает `getUpdates`; входящее соединение от Telegram не требуется. Сервис `telegram-poller` удалит существующий webhook при активации polling и хранит `update_id` в MariaDB.
- **Webhook:** требует публичный HTTPS `APP_URL`. Настройте/сгенерируйте webhook secret, выберите Webhook и нажмите **Установить webhook Telegram**.

Если прямой доступ к `api.telegram.org` фильтруется, используйте отдельный блок прокси Telegram. Поддерживаются `http://`, `https://`, `socks5://`, `socks5h://`. Схема описывает **сам прокси**, а не Telegram. Поэтому обычный HTTP-прокси для доступа к HTTPS Telegram задаётся как `http://proxy:port`.

Прокси используется для проверки соединения, исходящих сообщений, API webhook и Long polling.

Порядок привязки пользователя и диагностика описаны в разделе [Уведомления](notifications.ru.md).

## Исходящие webhooks

Раздел **Администрирование → Webhooks** управляет общесистемными подписками на доменные события. Для подписки выбираются endpoint и типы событий. Signing secret генерируется TMS, показывается открытым только при создании/ротации и хранится зашифрованным тем же ключевым механизмом, что системные notification credentials.

Webhook worker отправляет JSON асинхронно, подписывает точное тело HMAC-SHA256 по строке `timestamp.body`, сохраняет HTTP status/error и выполняет retry с backoff. После исправления endpoint неуспешную доставку можно повторить вручную. Подробный протокол, заголовки и проверка подписи описаны в [руководстве Webhooks](webhooks.ru.md).

Для Docker/Portainer должен быть запущен отдельный `webhook-worker`; при нативной установке регулярно запускайте `php bin/webhooks.php`.

## Backup и обновления

`tms-db`, `tms-attachments` и `tms-secrets` рассматривайте как единый комплект резервной копии. Перед обновлением или восстановлением прочитайте [руководство по установке](INSTALLATION.ru.md).

## Восстановление пароля

Браузерное восстановление может использовать email и/или привязанный Telegram. Владелец self-hosted установки всегда может выдать или применить reset локально из контейнера. См. [Восстановление доступа](ACCOUNT_RECOVERY.ru.md).

## Операционные проверки

После изменений полезно проверить:

```bash
docker compose -f compose.portainer.yaml ps
docker compose -f compose.portainer.yaml logs --tail=100 app
docker compose -f compose.portainer.yaml logs --tail=100 notifier
docker compose -f compose.portainer.yaml logs --tail=100 webhook-worker
docker compose -f compose.portainer.yaml logs --tail=100 telegram-poller
```

Не включайте `APP_DEBUG` на доступной из Интернета production-инсталляции, кроме короткого контролируемого окна диагностики.

## Интеграции с ИИ (MCP)

Для бессрочного токена укажите 0 дней. По умолчанию срок остаётся 30 дней. Бессрочный токен хранится с NULL в поле expires_at и действует до отзыва или блокировки учётной записи.

TMS предоставляет stateless Streamable HTTP MCP по адресу APP_URL + /mcp. Поддерживаются версии протокола 2025-03-26, 2025-06-18 и 2025-11-25, JSON-ответы, initialize, ping и инструменты. GET/DELETE возвращают 405, SSE-поток и сессии MCP не используются. OAuth discovery доступен с 0.6.1; протокол 2026-07-28 и прямое подключение ChatGPT пока не проверены. Нужен клиент с поддержкой Bearer-заголовка либо доверенный адаптер; не передавайте токен публичным прокси.

Пользователь управляет токенами в разделе «Профиль → Интеграции с ИИ (MCP)». Для выпуска нужен текущий пароль, секрет показывается один раз. По умолчанию доступ только на чтение. Запись разрешает изменение проектов, задач и чек-листов в рамках существующих личных и командных прав пользователя; административные действия и удаление задач не доступны. Для окончательного удаления нужен отдельный уровень прав «Чтение, запись и удаление задач». Старые токены сохраняют области прав; tools/list возвращает 25, 61 или 75 инструмент в зависимости от области. Клиент должен получать схемы динамически, а не фиксировать число инструментов. Изменение проекта разрешено владельцу или тимлиду, перенос задачи — её автору. Квитанции операций над проектами и задачами хранят идентификаторы разных сущностей. Токены хранятся в виде SHA-256, просроченные, отозванные и принадлежащие неактивным/неодобренным учётным записям не принимаются. Неиспользуемые токены отзывайте явно; смена пароля не отзывает MCP-токены автоматически.

Администратор также может управлять токенами из контейнера приложения:

    docker compose exec app php bin/mcp-token.php issue USER Codex read 30
    docker compose exec app php bin/mcp-token.php issue USER Codex-write write 30
    docker compose exec app php bin/mcp-token.php issue USER Codex-permanent write 0
    docker compose exec app php bin/mcp-token.php issue USER ChatGPT delete 0
    docker compose exec app php bin/mcp-token.php list USER
    docker compose exec app php bin/mcp-token.php revoke USER ID

Используйте HTTPS и доверенный обратный прокси с передачей Authorization; не журналируйте этот заголовок. Храните секреты в защищённом хранилище клиента, не в Git, истории команд или чатах. Запросы с браузерным Origin отклоняются. Настройте обычные ограничения размера и частоты запросов на прокси. Новый сервис или порт не нужен. Миграции добавляют mcp_tokens и mcp_mutations; таблицы входят в обычную резервную копию БД.

Каждая операция записи требует уникальный request_key (1–128 ASCII-символов: буквы, цифры и _ . : -). При повторе передавайте тот же ключ и аргументы. Сервер сериализует операции по токену, записывает идентификатор токена, имя инструмента, хеш аргументов, идентификатор задачи и время; изменения, события и аудит фиксируются одной транзакцией. Для удаления обязательны confirmed=true и точные ID (1–100 уникальных ID для массового удаления). Если хотя бы одна задача недоступна, не удаляется ни одна. Записи, события и квитанция удаления фиксируются одной транзакцией; физические файлы очищаются после commit, при повторе исходного ключа очистка повторяется. Ошибки очистки журналируются и возвращаются клиенту. Разные ключи могут создавать одинаковые задачи. Штатная история и правила уведомлений сохраняются.

Для проверки на изолированной БД выпустите токены записи, чтения и другого пользователя и выполните tests/smoke/mcp.py с переменными APP_URL, MCP_WRITE_TOKEN, MCP_READ_TOKEN и MCP_FOREIGN_TOKEN. Для полных браузерных и командных проверок также укажите MCP_TEST_USER, MCP_TEST_PASSWORD, MCP_FOREIGN_USER и MCP_FOREIGN_PASSWORD тестовых учётных записей.


В 0.5.4 общие квитанции MCP также хранят идентификаторы справочников и наборов изменённых задач, без содержимого пользовательских полей. Атомарное редактирование блокирует задачи в порядке ID и откатывает изменения целиком при ошибке. Токен удаления и явное confirmed=true обязательны при удалении повторения или справочника и замене типа/вариантов пользовательского поля. Клиенты должны поддерживать вложенные JSON Schema (anyOf, object, array) для пользовательских значений и фильтров. OAuth реализован в 0.6.1.


В 0.5.5 MCP поддерживает команды, приглашения, обсуждения и вложения задач/проектов. Прежние токены сохраняют области доступа, но получают новые инструменты соответствующей области. Для приглашений, ответа на приглашение и изменения ролей требуется явное подтверждение; удаление команды, участника, приглашения, комментария или вложения требует области удаления и подтверждения. Приглашения отправляются штатным сервисом после фиксации транзакции, повтор request_key не отправляет их вновь. Ошибки доставки не отменяют созданное приглашение. Вложения загружаются как base64 до 128 КиБ за запрос (либо меньше согласно настройкам); чтение порциями до 32 КиБ. Для более крупных файлов в 0.6.0 используйте возобновляемую загрузку. Применяются существующие проверки размера, расширения и фактического MIME. Файлы хранятся вне public; пути и ключи хранения не возвращаются клиенту. Удаление файла выполняется после коммита, повтор запроса повторяет очистку. При ошибке записи метаданных временный файл удаляется; внезапное завершение процесса может оставить бесхозный файл, как и при обычной загрузке.


### MCP 0.6.0: пользовательские операции и совместимость

Доступны 25 инструментов чтения, 61 при чтении/записи, 75 с правом удаления. Все прежние имена инструментов и аргументы сохранены. Область токена определяет доступные операции, а права владельца токена определяют доступ к объектам. Существующие токены получают расширенный набор инструментов в рамках той же области — при необходимости отзовите и замените токен на более ограниченный.

Для возобновляемых загрузок добавлены таблицы mcp_attachment_uploads и mcp_attachment_chunks; они содержат незавершённые данные пользователя. Не более четырёх загрузок на пользователя, срок жизни 24 часа. Данные удаляются при отмене, завершении, удалении пользователя или целевого объекта; периодический обработчик recurring.php удаляет просроченные записи. Содержимое передаётся порциями 128 КиБ (последняя — остаток), проверяются последовательность, полный размер, SHA-256, права и штатная политика вложений. Обычные небольшие загрузки продолжают работать. Внезапная остановка между записью итогового файла и коммитом БД всё ещё может оставить бесхозный файл; плановое удаление просроченных частей не удаляет опубликованные вложения.

Передача проекта требует явного подтверждения и прав на исходный проект и целевую команду. Удаление проекта через MCP разрешено только для проекта без задач и с областью удаления; очистка вложений повторяется при повторе request_key. Удаление непустого личного проекта через веб-интерфейс остаётся отличием: в MCP сначала выполните явные переносы задач, чтобы избежать незаметной потери значений. Настройки каналов и расписаний уведомлений доступны без раскрытия или замены адресов доставки и привязок. Операции управления учётными данными и администрирование исключены намеренно. OAuth реализован в 0.6.1.


Подключение через OAuth: [руководство OAuth 0.6.1](MCP_OAUTH.ru.md).
