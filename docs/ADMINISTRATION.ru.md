# Администрирование

Это канонический учебник администратора/оператора TMS. Он охватывает развёртывание, общесистемные настройки, управление аккаунтами, worker-процессы, backup/restore, обновления, вебхуки, диагностику и обязанности по документации релиза.

[TOC]

## Архитектура развёртывания

Эталонная self-hosted установка состоит из:

- **app** — Apache/PHP веб-приложение; при старте выполняет миграции БД;
- **db** — постоянная MariaDB;
- **notifier** — генерация recurring tasks и плановые уведомления;
- **webhook-worker** — восстановление очереди и доставка исходящих вебхуков;
- **telegram-poller** — постоянный получатель команд Telegram при режиме Long polling;
- постоянных volumes БД, вложений и ключей шифрования.

Через reverse proxy обычно публикуется только **app**. MariaDB и worker-сервисы остаются внутри deployment network.

### Пример: первый запуск Docker/Portainer

1. Скопируйте `.env.example` в защищённую конфигурацию окружения.
2. Задайте минимум `DB_PASS`, `APP_URL`, `APP_TIMEZONE`, `APP_LOCALE`, `SESSION_SECURE`.
3. Разверните `compose.portainer.yaml` как стек Portainer либо обычным Docker Compose.
4. Дождитесь статуса healthy у **app**.
5. Создайте первого администратора из контейнера app.
6. Войдите и настройте системные уведомления/вебхуки при необходимости.
7. До загрузки реальных production-данных сделайте первую резервную копию.

Полный список переменных окружения и reverse-proxy требования см. в [Установке](INSTALLATION.ru.md).

## Первый администратор

Создайте первого администратора из контейнера приложения:

```bash
php bin/create-admin.php admin admin@example.com
```

После входа административные разделы доступны из пользовательского/административного меню.

Для Portainer/Compose:

```bash
docker compose -f compose.portainer.yaml exec app \
  php bin/create-admin.php admin admin@example.com
```

Не передавайте реальный production-пароль через командную строку так, чтобы он остался в shell history или оказался в compose-файле репозитория.

## Пользователи и регистрация

Открытая регистрация управляется `REGISTRATION_ENABLED`.

При включённой регистрации ссылки подтверждения email строятся от `APP_URL`. Если `REGISTRATION_AUTO_APPROVE_AFTER_EMAIL=true`, подтверждение email одновременно одобряет аккаунт. Значение `false` требует ручного одобрения в **Администрирование → Ожидающие пользователи**.

Администратор может напрямую создавать пользователей, менять роль и активность, одобрять аккаунты, вручную подтверждать email, повторно отправлять письмо подтверждения, смотреть детали пользователя и временно входить от его имени для диагностики.

Пользователя нельзя отключить или удалить, если он остаётся единственным тимлидом хотя бы одной команды. Сначала назначьте другого участника тимлидом — это не позволяет административной операцией оставить команду без управления.

## Справочники и пользовательские поля

Статусы, типы задач, заказчики и дополнительные поля принадлежат конкретному пользователю. Они не становятся глобальными только потому, что владелец — администратор.

Для статусов доступны порядок, статус по умолчанию и статус завершения. Принадлежность статусов/типов/заказчиков защищается и приложением, и ограничениями БД.

Пользовательские поля: текст, многострочный текст, список, деньги, checkbox и список checkbox. При изменении набора вариантов значения, которые больше недопустимы, могут быть очищены/урезаны.

## SMTP

Откройте **Администрирование → Системные уведомления**. Укажите сервер, порт, TLS/SSL, логин/пароль и отправителя, включите транспорт, сохраните и нажмите **Отправить тестовое письмо SMTP**.

Пароль SMTP хранится зашифрованным. Ключ — либо внешний `NOTIFICATION_SECRET`, либо автоматически созданный ключ в volume `tms-secrets`.

## Telegram

Создайте бота через BotFather, затем задайте имя и token в **Администрирование → Системные уведомления**. Сначала используйте **Проверить соединение с Telegram**.

Для получения команд выберите один режим:

- **Long polling (рекомендуется):** TMS сам вызывает `getUpdates`; входящее соединение от Telegram не требуется. Сервис `telegram-poller` удалит существующий webhook при активации polling и хранит `update_id` в MariaDB.
- **Webhook:** требует публичный HTTPS `APP_URL`. Настройте/сгенерируйте webhook secret, выберите Webhook и нажмите **Установить webhook Telegram**.

Если прямой доступ к `api.telegram.org` фильтруется, используйте отдельный блок прокси Telegram. Поддерживаются `http://`, `https://`, `socks5://`, `socks5h://`. Схема описывает **сам прокси**, а не Telegram. Поэтому обычный HTTP-прокси для доступа к HTTPS Telegram задаётся как `http://proxy:port`.

Прокси используется для проверки соединения, исходящих сообщений, API webhook и Long polling.

Порядок привязки пользователя и диагностика описаны в разделе [Уведомления](notifications.ru.md).

## Исходящие вебхуки

Откройте **Администрирование → Вебхуки**, чтобы связать доменные события TMS с автоматизацией, мониторингом или агентами.

Для каждой подписки:

1. задайте понятное название;
2. укажите HTTP/HTTPS URL получателя;
3. выберите только действительно нужные типы событий;
4. создайте подписку;
5. сразу скопируйте сгенерированный секрет подписи — открытым он показывается один раз;
6. настройте на получателе проверку `X-TMS-Signature` и допустимого возраста timestamp;
7. создайте безопасное тестовое событие и проверьте историю доставки.

Доставка асинхронная. `webhook-worker` восстанавливает пропущенные queue-записи из устойчивого журнала событий, подписывает запросы и повторяет неудачные доставки. Недоступный внешний сервис не блокирует работу пользователей в TMS.

Управление вебхуками намеренно доступно только администраторам. Внутренние/private endpoints разрешены, потому что self-hosted агенты часто находятся в той же сети. Поэтому права управления вебхуками эквивалентны доверию оператору инфраструктуры.

Протокол HMAC и retry-policy описаны в [Вебхуках](webhooks.ru.md).

## Фоновые worker-процессы

### notifier

Запускает:

- `bin/recurring.php` — создаёт новые экземпляры recurring tasks;
- `bin/notify.php` — создаёт и доставляет плановые напоминания.

Стандартный интервал: `NOTIFICATION_INTERVAL_SECONDS=60`.

### webhook-worker

Запускает `bin/webhooks.php`:

- сверяет durable domain-event journal с активными подписками;
- отправляет наступившие доставки;
- планирует retry/backoff;
- записывает историю результатов.

Стандартный интервал: `WEBHOOK_INTERVAL_SECONDS=15`.

На одну БД запускайте один webhook-worker.

### telegram-poller

Постоянно работает только в режиме Telegram Long polling. Поток update должен обслуживаться одним poller на БД.

### Быстрая проверка worker'ов

```bash
docker compose -f compose.portainer.yaml ps
docker compose -f compose.portainer.yaml logs --tail=100 notifier
docker compose -f compose.portainer.yaml logs --tail=100 webhook-worker
docker compose -f compose.portainer.yaml logs --tail=100 telegram-poller
```

Worker можно перезапускать отдельно от web-приложения. Recurrence, дедупликация уведомлений и webhook delivery рассчитаны на повторные запуски.

## Backup и обновления

`tms-db`, `tms-attachments` и `tms-secrets` рассматривайте как единый комплект резервной копии. Один dump БД не является полноценным backup TMS.

### Порядок резервного копирования

1. Запишите точную версию/image tag работающей TMS.
2. Сделайте согласованный dump MariaDB.
3. Скопируйте/архивируйте volume вложений.
4. Скопируйте/архивируйте volume секретов с ключом шифрования уведомлений.
5. Храните все части под одним идентификатором/датой backup.
6. Проверьте, что dump читается, а архивы не пустые.
7. Периодически выполняйте пробное восстановление на изолированном экземпляре.

Пример dump:

```bash
docker compose -f compose.portainer.yaml exec -T db \
  mariadb-dump -utms -p"$DB_PASS" --single-transaction --routines --triggers tms \
  > tms-$(date +%F).sql
```

Volumes сохраняйте средствами Docker/Portainer. Их фактические имена могут иметь prefix стека, поэтому проверяйте `docker volume ls`, а не копируйте имя из документации вслепую.

### Порядок восстановления

1. Закройте пользовательский трафик к целевому экземпляру.
2. Восстановите volume секретов **до** проверки SMTP/Telegram/webhook credentials.
3. Восстановите вложения.
4. Восстановите БД в совместимую MariaDB.
5. Разверните image-версию, соответствующую схеме backup.
6. Запустите приложение и дождитесь health checks.
7. Проверьте вход, одно вложение, настройки уведомлений и worker'ы.
8. Только затем возвращайте пользовательский трафик.

### Порядок обновления

1. Прочитайте release notes и замечания по миграциям.
2. Сделайте полный backup-комплект.
3. Разверните новый versioned image.
4. Дождитесь выполнения миграций и healthy у **app**.
5. Проверьте **notifier**, **webhook-worker** и Telegram worker.
6. Выполните короткий функциональный тест: вход, создание/правка задачи, Calendar, Notifications.
7. Не удаляйте backup, пока новая версия не проработает нормальный для вашей эксплуатации контрольный период.

Миграции рассчитаны на движение вперёд. После несовместимого изменения схемы простая замена image на старый не гарантирует rollback — для настоящего отката восстанавливайте соответствующий backup.

Перед обновлением или восстановлением прочитайте [руководство по установке](INSTALLATION.ru.md).

## Восстановление пароля

Браузерное восстановление может использовать email и/или привязанный Telegram. Владелец self-hosted установки всегда может выдать или применить reset локально из контейнера. См. [Восстановление доступа](ACCOUNT_RECOVERY.ru.md).

## Диагностика типовых проблем

### Приложение unhealthy

```bash
docker compose -f compose.portainer.yaml ps
docker compose -f compose.portainer.yaml logs --tail=200 app
docker compose -f compose.portainer.yaml logs --tail=200 db
```

Проверьте health MariaDB, ошибки миграций, обязательные переменные окружения и права записи в `var/`.

### Пользователи входят, но напоминания не приходят

1. Убедитесь, что `notifier` запущен.
2. Проверьте пользовательские настройки уведомлений.
3. Убедитесь, что задача не находится в completion status.
4. Проверьте, что пользователь является владельцем/исполнителем и не потерял доступ к проекту/команде.
5. Отдельно проверьте SMTP/Telegram test delivery и само правило напоминания.

### Вебхук долго остаётся pending/retry

1. Посмотрите логи `webhook-worker`.
2. Откройте историю в **Администрирование → Вебхуки**.
3. Проверяйте DNS/сетевую доступность **из контейнера worker**, а не только с Docker-хоста.
4. Получатель должен отвечать 2xx без redirect.
5. После ротации секрета получатель должен использовать новый секрет.
6. Нажимайте ручной Retry только после устранения проблемы endpoint.

### Telegram перестал принимать команды

Проверьте выбранный delivery mode, bot token, proxy и что при Long polling работает ровно один poller. Переход на Long polling удаляет Telegram webhook; режим Webhook требует публичный HTTPS `APP_URL`.

### После restore перестали расшифровываться SMTP/Telegram/webhook credentials

БД была восстановлена без соответствующего ключа из `tms-secrets`. Восстановите secret volume из того же backup-комплекта. Новый ключ не сможет расшифровать ciphertext старого ключа.

## Операционные проверки

После изменений полезно проверить:

```bash
docker compose -f compose.portainer.yaml ps
docker compose -f compose.portainer.yaml logs --tail=100 app
docker compose -f compose.portainer.yaml logs --tail=100 notifier
docker compose -f compose.portainer.yaml logs --tail=100 webhook-worker
docker compose -f compose.portainer.yaml logs --tail=100 telegram-poller
```

Не включайте `APP_DEBUG` на доступной из Интернета production-инсталляции, кроме короткого контролируемого окна диагностики.


## Поддержка документации при релизах

Пользовательский и администраторский учебники являются частью релиза, а не необязательными заметками. Изменение поведения или конфигурации обязано обновлять затронутый английский **и** русский исходник учебника в том же pull request.

CI выполняет documentation-impact check и собирает HTML/PDF. Stable/preview release прикладывает сгенерированные файлы к GitHub Release.

Каноническая политика: [DOCUMENTATION_POLICY.md](DOCUMENTATION_POLICY.md).
