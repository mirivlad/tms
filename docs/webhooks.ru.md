# Вебхуки

Вебхуки TMS доставляют устойчивые доменные события во внешние системы автоматизации, мониторинга и агентам.

Подписки на вебхуки являются **системной настройкой администратора**. Обычные пользователи не могут создавать произвольные исходящие HTTP-вызовы.

## 1. Создание подписки

Откройте **Администрирование → Вебхуки** и укажите:

- понятное название;
- HTTP- или HTTPS-адрес получателя;
- один или несколько типов доменных событий;
- активна ли подписка.

TMS генерирует случайный секрет подписи. Открытый секрет показывается **один раз** сразу после создания подписки или ротации секрета. В этот момент сохраните его в системе-получателе.

Секрет хранится в TMS в зашифрованном виде тем же ключом экземпляра, которым защищены учётные данные уведомлений.

## 2. Доставка события

Сначала доменное событие записывается в устойчивый журнал `domain_events`. Затем для подходящих активных подписок создаются строки в устойчивой очереди `webhook_deliveries`.

Отдельный worker выполняет HTTP-доставку асинхронно. Медленный или недоступный внешний сервис поэтому не блокирует действие пользователя, породившее событие.

Compose- и Portainer-шаблоны запускают отдельный сервис `webhook-worker`. Стандартный интервал проверки — 15 секунд:

```dotenv
WEBHOOK_INTERVAL_SECONDS=15
```

При нативной установке запускайте:

```bash
php bin/webhooks.php
```

по короткому расписанию. На одну БД должен работать один webhook-worker.

## 3. HTTP-запрос

TMS отправляет `POST` с JSON-телом и не следует HTTP-редиректам.

Важные заголовки:

| Заголовок | Значение |
| --- | --- |
| `X-TMS-Webhook-Version` | Версия протокола доставки, сейчас `1` |
| `X-TMS-Delivery-Id` | Идентификатор записи доставки |
| `X-TMS-Event-Id` | Стабильный UUID доменного события |
| `X-TMS-Event-Type` | Тип события, например `task.updated` |
| `X-TMS-Timestamp` | Unix timestamp, участвующий в подписи |
| `X-TMS-Signature` | `v1=<hex HMAC-SHA256>` |

Пример payload:

```json
{
  "id": "11111111-2222-4333-8444-555555555555",
  "type": "task.updated",
  "schema_version": 1,
  "occurred_at": "2026-09-23 12:34:56.123456",
  "actor": {
    "user_id": 7,
    "username": "alice"
  },
  "subject": {
    "task_id": 42,
    "project_id": 10,
    "comment_id": null
  },
  "visibility": {
    "user_id": null,
    "team_id": 3
  },
  "data": {
    "subject_title": "Deploy TMS",
    "changes": {
      "status": {
        "old": "Todo",
        "new": "Done"
      }
    }
  }
}
```

Полный контракт доменных событий описан в [DOMAIN_EVENTS.md](DOMAIN_EVENTS.md).

## 4. Проверка подписи

В подпись входит точное UTF-8 тело запроса с timestamp перед ним:

```text
<TIMESTAMP>.<RAW_REQUEST_BODY>
```

Вычислите:

```text
hex(HMAC-SHA256(signing_secret, timestamp + "." + raw_body))
```

и в постоянное время сравните результат с шестнадцатеричной частью `X-TMS-Signature`.

Псевдокод:

```text
expected = "v1=" + hmac_sha256_hex(secret, timestamp + "." + raw_body)
constant_time_compare(expected, request_header["X-TMS-Signature"])
```

Получателю также стоит отклонять слишком старые timestamp и дедуплицировать обработку по `X-TMS-Event-Id`.

Нельзя сначала разобрать JSON и собрать его заново: подпись проверяется по исходным байтам тела, полученным от TMS.

## 5. Успех, повторные попытки и окончательная ошибка

Любой HTTP-код от `200` до `299` считается успешной доставкой.

Сетевые ошибки и ответы не-2xx переводят доставку в retry с увеличивающимся интервалом:

1. 1 минута;
2. 5 минут;
3. 15 минут;
4. 1 час;
5. 6 часов;
6. 24 часа;
7. 48 часов.

Восьмая неудачная попытка переводит доставку в окончательное состояние `failed`.

На странице **Администрирование → Вебхуки** видны последние доставки, HTTP-код, последняя ошибка и число попыток. Окончательно неудачную доставку можно вручную снова поставить в очередь.

## 6. Восстановление после сбоя постановки в очередь

Каноническим источником остаётся журнал доменных событий. Перед обычной доставкой worker сверяет активные подписки с `domain_events` и восстанавливает отсутствующие строки `webhook_deliveries`, подходящие подписке с момента её текущей активации/конфигурации.

Поэтому временный сбой синхронной постановки в очередь не приводит к безвозвратной потере события.

## 7. Изменение подписки

Изменение endpoint или набора событий создаёт новую точку активации и удаляет ещё не отправленные pending/retry-доставки старой конфигурации. История завершённых и окончательно неудачных доставок сохраняется.

Изменение только названия не удаляет очередь.

Отключение подписки прекращает доставку и очищает её pending/retry-очередь. При повторном включении обработка начинается с нового момента активации, без проигрывания всего старого журнала.

Ротация секрета не меняет endpoint и список событий. Все последующие попытки подписываются уже новым секретом.

## 8. Безопасность

- управление вебхуками доступно только администраторам;
- URL со встроенными логином/паролем отклоняются;
- секрет подписи генерируется TMS и хранится зашифрованным;
- TMS намеренно разрешает администратору внутренние/private endpoints: в self-hosted-сценарии агенты и интеграции часто живут в той же сети;
- права администратора вебхуков следует считать полномочиями оператора инфраструктуры;
- при выходе трафика из доверенной сети используйте HTTPS;
- до обработки запроса проверяйте подпись и допустимый возраст timestamp;
- делайте обработчик идемпотентным по event id.

## 9. Поддерживаемые события

Список выбора строится из стабильного каталога доменных событий:

- создание/изменение/удаление задач;
- жизненный цикл checklist;
- создание/изменение/удаление проектов;
- создание/изменение/удаление комментариев обсуждений.

В следующих релизах могут добавляться новые типы событий. Совместимость существующих имён и payload регулируется правилами из [DOMAIN_EVENTS.md](DOMAIN_EVENTS.md).
