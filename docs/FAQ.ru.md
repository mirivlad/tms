# FAQ

## Какой Docker-образ использовать?

Для обычной установки используйте фиксированный stable, например `ghcr.io/mirivlad/tms:v0.1.3`. `latest` следует за стабильными релизами. `edge` — проверенный CI `main`, но это канал для тех, кто сознательно хочет development-сборки.

## Обновление удалит мои задачи?

Нет, если сохранены именованные volumes. Обычное обновление заменяет контейнеры/образы, но оставляет `tms-db`, `tms-attachments` и `tms-secrets`. Не удаляйте volumes при штатном обновлении.

## Почему по HTTP надо ставить `SESSION_SECURE=false`?

Cookie с флагом Secure браузер не отправляет по обычному HTTP. Production с HTTPS должен использовать `SESSION_SECURE=true`; для прямого HTTP-теста требуется `false`.

## Забыл пароль администратора, а почта не настроена. Доступ потерян?

Нет. Используйте локальное восстановление из консоли контейнера, описанное в [Восстановлении доступа](ACCOUNT_RECOVERY.ru.md).

## Бот молчит после команды `/link_...`. Что проверять?

Сначала **Проверить соединение с Telegram** в админке. Затем выбранный режим получения команд. Для Long polling должен работать `telegram-poller`; Webhook требует, чтобы Telegram мог подключиться к `APP_URL/telegram/webhook` из Интернета. Если входящий трафик Telegram фильтруется, выбирайте Long polling.

## Telegram работает по HTTPS. Значит HTTP-прокси надо писать как `https://`?

Нет. Схема описывает сам прокси. Для обычного HTTP CONNECT proxy используйте `http://host:port`; HTTPS-соединение с Telegram пройдёт через него.

## Long polling или Webhook?

По умолчанию удобнее Long polling, особенно за NAT, при фильтрации или использовании proxy. Webhook имеет смысл при надёжно доступном из Telegram публичном HTTPS endpoint.

## Можно настроить SMTP и Telegram без env-переменных?

Да. Основной путь — **Администрирование → Системные уведомления**. Telegram env остаются bootstrap/fallback. SMTP хранится в БД.

## Что будет при потере `tms-secrets`?

Задачи не исчезнут, но сохранённые зашифрованные SMTP/Telegram-реквизиты нельзя будет расшифровать. Введите их заново или восстановите соответствующий ключ. При внешнем `NOTIFICATION_SECRET` резервируйте именно его.

## Пользователи видят задачи друг друга?

Нет. Текущая модель изолирует пользовательские данные по владельцу. Будущая командная работа не должна строиться на ослаблении этой границы.

## Почему статусы не перевелись при смене языка?

Язык интерфейса и пользовательские данные разделены. TMS не переименовывает существующие статусы, типы и метаданные. Начальные справочники нового пользователя создаются на языке установки.

## Почему время уведомления может отличаться от часового пояса профиля?

Фоновый планировщик сейчас рассчитывает время отправки по `APP_TIMEZONE`. Web-интерфейс в соответствующих местах использует timezone профиля. Если важна единая «настенная» привязка уведомлений, правильно задайте timezone установки.

## Где лежат вложения?

По умолчанию в volume `tms-attachments`, вне публичного web-root. Резервируйте его вместе с БД.

## Надо публиковать порт MariaDB наружу?

Нет. Стандартные Compose-файлы его не публикуют. Наружу выводится только HTTP приложения, обычно за reverse proxy.

## Можно запретить публичную регистрацию?

Да. По умолчанию `REGISTRATION_ENABLED=false`. Администратор при этом всё равно может создавать пользователей вручную.

## Как сообщить об уязвимости?

Не публикуйте эксплуатационные детали в открытом issue. Следуйте [SECURITY.md](../SECURITY.md).
